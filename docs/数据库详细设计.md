# 10 数据库详细设计

## 10.1 数据库总体设计

### 10.1.1 设计目标

统一认证中心数据库主要用于持久化以下数据：

1. 用户身份数据；
2. 行政区划数据；
3. 单位及组织机构数据；
4. 部门数据；
5. 岗位/职务数据；
6. 用户与组织机构之间的任职关系；
7. 用户主任职信息；
8. 用户密码历史及安全状态；
9. 认证中心管理员角色及管理权限；
10. 登录日志；
11. 操作审计日志；
12. OAuth2/OIDC 客户端、授权、Token、Scope 等协议数据。

数据库设计遵循以下原则：

- **统一身份、分散授权**；
- **用户与组织机构解耦**；
- **支持一人多职、多单位任职**；
- **主任职独立管理**；
- **认证中心管理权限与业务系统授权严格隔离**；
- **OAuth2/OIDC 协议数据由 OpenIddict 管理**；
- **不在认证中心数据库保存业务角色、业务权限及 DataScope**；
- **尽量使用跨数据库通用的数据类型和约束**；
- **业务领域模型不直接依赖具体数据库产品**；
- **数据库厂商差异集中在 Infrastructure 数据访问层处理**。

---

## 10.1.2 数据库选型及兼容矩阵

V3.0 采用数据库可替换设计，生产环境最终只选择一种数据库产品，不要求同一套生产环境同时运行多个数据库。

| 数据库 | EF Core | .NET | 定位 |
|---|---|---|---|
| 金仓数据库 | EF Core 10 | .NET 10 | **首选生产方案** |
| 达梦数据库 | EF Core 9 | .NET 9 | 备选方案 |
| OceanBase | EF Core 8 | .NET 8 | 备选方案 |

数据库访问层不得依赖以下数据库特性：

- MySQL `AUTO_INCREMENT` 专有写法；
- MySQL `TINYINT` 业务逻辑强依赖；
- MySQL 专有函数；
- MySQL JSON 专有类型；
- MySQL 特有字符集排序规则；
- 数据库厂商专有存储过程；
- 数据库厂商专有分页语法。

数据库中的 JSON 类业务快照统一按照字符串文本保存，由应用层完成序列化和反序列化。

# 10.3 数据库命名规范

## 10.3.1 表命名

统一采用：

```text
sys_xxx
```

OpenIddict 框架表按照 OpenIddict 官方持久化模型生成。

## 10.3.2 字段命名

统一采用小写蛇形命名：

```text
user_id
login_name
create_time
update_time
token_version
```

## 10.3.3 主键

业务表统一采用：

```text
id bigint
```

由应用层生成全局唯一 ID，推荐采用雪花算法或其他分布式 ID 方案。

这样可以避免不同国产数据库自增机制差异。

## 10.3.4 时间字段

统一采用：

```text
timestamp / datetime
```

具体由 EF Core Provider 映射。

所有服务器统一使用北京时间或统一 UTC 策略，项目实施阶段确定一种方案后全系统保持一致。

# 10.4 sys_user 用户表

## 10.4.1 表说明

`sys_user` 用于保存统一认证中心用户的基础身份信息、账号状态及安全状态。

该表只保存用户身份信息，不保存业务角色、业务权限和 DataScope。

## 10.4.2 字段设计

| 字段 | 类型 | 非空 | 默认值 | 说明 |
|---|---|---:|---|---|
| id | bigint | 是 | - | 主键 |
| login_name | varchar(100) | 是 | - | 登录账号，全局唯一 |
| password_hash | varchar(512) | 是 | - | 密码哈希 |
| real_name | varchar(100) | 是 | - | 真实姓名 |
| mobile | varchar(32) | 否 | NULL | 手机号 |
| email | varchar(200) | 否 | NULL | 邮箱 |
| id_card_ciphertext | varchar(1024) | 否 | NULL | 身份证密文 |
| id_card_hash | varchar(128) | 否 | NULL | 身份证查询哈希 |
| status | integer | 是 | 0 | 用户状态 |
| login_fail_count | integer | 是 | 0 | 连续登录失败次数 |
| lock_until | timestamp | 否 | NULL | 锁定截止时间 |
| must_modify_pwd | integer | 是 | 0 | 是否强制修改密码 |
| password_expire_time | timestamp | 否 | NULL | 密码过期时间 |
| security_stamp | varchar(128) | 否 | NULL | 安全标识 |
| token_version | bigint | 是 | 1 | Token 安全版本 |
| last_login_time | timestamp | 否 | NULL | 最近登录时间 |
| last_login_ip | varchar(64) | 否 | NULL | 最近登录 IP |
| create_time | timestamp | 是 | - | 创建时间 |
| update_time | timestamp | 是 | - | 修改时间 |
| is_deleted | integer | 是 | 0 | 逻辑删除 |

### 状态定义

```text
0 = 正常
1 = 禁用
2 = 锁定
```

- `status=1`：管理员主动禁用；
- `lock_until`：登录安全策略产生的临时锁定。

不建议仅依靠 `status` 表示临时锁定。

## 10.4.3 唯一约束

```text

(login_name)
```

登录名必须全局唯一。

## 10.4.4 索引

```text

(mobile)

(id_card_hash)
```

# 10.9 sys_user_organization 用户任职关系表

## 10.9.1 表说明

用户与组织机构之间采用多对多关系。

一个用户可以：

- 在一个单位任职；
- 在多个单位任职；
- 在一个单位多个部门任职；
- 同时拥有多个职务；
- 存在历史任职关系。

| is_deleted | integer | 是 | 逻辑删除 |


### 设计说明

```text

```

这样可以避免在多个国产数据库中依赖复杂条件唯一索引。

# 10.10 sys_user_main_organization 用户主任职表

## 10.10.1 表说明

该表用于明确记录用户当前唯一主任职。

一个用户最多只能存在一条主任职记录。

## 10.10.2 字段设计

| 字段 | 类型 | 非空 | 说明 |
|---|---|---:|---|
| id | bigint | 是 | 主键 |
| user_id | bigint | 是 | 用户 ID |
| user_organization_id | bigint | 是 | 用户任职关系 ID |
| create_time | timestamp | 是 | 创建时间 |
| update_time | timestamp | 是 | 修改时间 |

## 10.10.3 唯一约束

```text
UK_sys_user_main_org_user
(user_id)
```

保证：

```text
一个用户 = 最多一个主任职
```

同时：

```text
UK_sys_user_main_org_relation
(user_organization_id)
```

保证一条任职关系不会同时作为多个用户的主任职。

## 10.10.4 主任职变更

主任职变更必须在一个数据库事务中完成：

```text
BEGIN

1. 校验目标任职关系属于当前用户
2. 删除旧主任职
3. 创建新主任职
4. 更新相关缓存
5. 产生审计日志

COMMIT
```

不得仅通过修改 JWT 实现主任职变更。

# 10.12 认证中心管理角色与权限

## 10.12.1 设计原则

认证中心需要具备自身管理权限。

该权限体系仅用于保护：

```text
认证中心管理后台
认证中心管理 API
用户管理
组织机构管理
OAuth Client 管理
安全策略管理
审计日志查询
```

不用于：

```text
业务系统角色
业务系统菜单
业务系统按钮权限
业务系统 DataScope
```

原详细设计明确要求认证中心不得建设业务角色、业务权限、菜单、按钮权限、DataScope 等业务授权数据。

# 10.19 审计日志哈希链

V3.0 增加审计日志完整性设计。

每条日志计算：

```text
log_hash =
Hash(
    previous_hash
    + event_type
    + operation_type
    + operate_user_id
    + target_user_id
    + content
    + create_time
)
```

形成：

```text
日志1
  │
  └── hash1
        │
        ▼
日志2
  │
  └── previous_hash = hash1
        │
        └── hash2
              │
              ▼
日志3
```

当任意历史记录被修改时，后续哈希链校验将失败。

### 注意

哈希链属于**完整性校验机制**，不等同于绝对不可篡改。

对于高等级安全要求，可进一步将审计日志同步至：

- 独立审计服务器；
- WORM 存储；
- 专用日志审计系统；
- 密码设备；
- 具备不可篡改能力的存储系统。

# 10.20 OpenIddict 数据表

OAuth2/OIDC 数据采用 OpenIddict 管理。

原则：

> 业务代码不得直接操作 OpenIddict 框架表。

原 V2.0 已采用 OpenIddict，并明确由框架维护 Applications、Authorizations、Scopes、Tokens 等数据。

主要逻辑实体如下：

```text
OpenIddictApplications
OpenIddictAuthorizations
OpenIddictScopes
OpenIddictTokens
```

不同 OpenIddict 版本及数据库 Provider 生成的实际字段可能存在差异，因此 V3.0 不建议在设计文档中手写一份“固定 OpenIddict DDL”作为业务表。

# 10.21 OpenIddictApplications

用于保存 OAuth2 Client。

核心业务字段包括：

| 逻辑字段 | 说明 |
|---|---|
| Id | 框架主键 |
| ClientId | OAuth Client ID |
| ClientSecret | Client Secret |
| DisplayName | 客户端名称 |
| ConsentType | 授权确认方式 |
| RedirectUris | 回调地址 |
| PostLogoutRedirectUris | 登出回调地址 |
| Permissions | OAuth/OIDC 权限 |
| Requirements | PKCE 等要求 |
| ClientType | confidential/public |
| ApplicationType | 应用类型 |

业务系统注册 OAuth 客户端时，通过：

```text
OpenIddictApplicationManager
```

等官方 API 管理。

禁止：

```text
INSERT OpenIddictApplications
UPDATE OpenIddictApplications
DELETE OpenIddictApplications
```

由业务代码直接操作。

# 10.22 OpenIddictScopes

用于定义 OAuth Scope。

例如：

```text
openid
profile
email
organization.read
```

其中：

```text
openid
profile
email
```

属于标准 OIDC Scope。

认证中心可定义：

```text
organization.read
```

用于允许业务系统读取用户完整组织任职信息。

注意：

`organization.read` 只是 OAuth 数据访问 Scope，不是业务权限。

# 10.23 OpenIddictAuthorizations

用于保存 OAuth 授权记录。

主要用于：

- Authorization Code；
- 用户授权关系；
- Consent；
- Scope；
- Client 与用户之间的授权关系。

由 OpenIddict 自动维护。

---

# 10.24 OpenIddictTokens

用于管理 OAuth Token 生命周期相关数据。

包括：

- Authorization Code；
- Refresh Token；
- Reference Token（如启用）；
- Token 状态；
- Token 过期时间；
- Token 撤销状态。

Access Token 如果采用 JWT 自包含模式，业务 API 不需要每次请求查询该表。

业务 API 按照：

```text
signature
issuer
audience
expiration
```

完成本地验证。

原设计明确要求业务接口请求不回调用认证中心进行 Token 校验，而是在业务系统本地完成 JWT 验证。

# 10.25 Token Version 数据设计

`sys_user.token_version` 是 V3.0 用户安全状态的重要字段。

例如：

```text
用户当前 token_version = 5
```

签发 Token 时：

```text
token_version = 5
```

当发生以下事件时：

- 用户禁用；
- 管理员重置密码；
- 安全风险事件；
- 强制用户退出；
- 用户关键身份信息变更；

执行：

```text
token_version = token_version + 1
```

同时撤销 Refresh Token。

## 重要说明

普通模式下业务 API 不需要每次查询数据库。

Access Token 使用短 TTL，例如：

```text
10 分钟
```

因此旧 Access Token 最长在其 TTL 内自然失效。

高安全场景可以进一步使用：

```text
Introspection
```

或者安全版本同步机制，实现更加实时的 Token 失效。

---

# 10.26 身份证数据存储设计

身份证属于敏感身份信息。

数据库不得直接保存明文身份证号码。

采用：

```text
id_card_ciphertext
id_card_hash
```

两个字段。

## id_card_ciphertext

保存加密后的身份证号码。

例如：

```text
SM4 / AES
```

具体算法根据最终密码应用方案确定。

## id_card_hash

用于精确查询。

例如：

```text
HMAC-SHA256(idCard)
```

国密环境按照最终密码方案可采用相应国密算法。

查询：

```text
用户输入身份证
        ↓
后端计算 HMAC
        ↓
查询 id_card_hash
        ↓
获取用户
```

不需要对数据库中的所有密文逐条解密。

# 10.27 外键设计原则

考虑金仓、达梦、OceanBase 等数据库兼容性，业务表原则上建立明确的逻辑引用关系。

主要关系：

```text
sys_user
   │
   ├── sys_user_password_history
   │
   ├── sys_user_organization
   │       ├── sys_unit
   │       ├── sys_department
   │       ├── sys_position
   │       └── sys_region
   │
   └── sys_user_main_organization

sys_unit
   └── sys_department

sys_admin_role
   ├── sys_admin_user_role
   └── sys_admin_role_permission
            │
            └── sys_admin_permission
```

对于删除操作，不建议依赖数据库级联删除。

统一采用：

```text
业务校验
+
逻辑删除
+
状态控制
```

避免误删历史身份和审计数据。

# 10.28 删除策略

## 用户

禁止直接物理删除。

采用：

```text
is_deleted = 1
```

同时：

```text
token_version++
Refresh Token 全部撤销
```

## 单位

如果仍存在：

- 部门；
- 用户任职；
- 主任职；
- 历史业务关联；

则不得物理删除。

优先：

```text
status = disabled
```

## 部门

如果仍有用户任职关系，不允许直接删除。

## 岗位/职务

存在历史任职关系时，不进行物理删除。

## 审计日志

禁止修改、禁止删除。

```text
    校验任职关系

    创建新主任职
    更新安全相关缓存
    写入审计
```

```text

    写入审计
```

```text

    设置 must_modify_pwd
    写入审计
COMMIT
```

# 10.31 数据库安全设计

## 10.31.1 数据库账号分离

至少划分：

```text

auth_audit
auth_dba
```

其中应用账号原则上只拥有业务运行所需权限。

## 10.31.2 审计账号

审计数据建议单独设置写入权限：

```text
INSERT

```

禁止：

```text
UPDATE
DELETE
```

## 10.31.3 敏感字段

以下数据需要重点保护：

```text

id_card_ciphertext
id_card_hash
security_stamp
token_version
client_secret
OAuth Token 数据
审计数据
```

其中：

```text
Client Secret
私钥
签名密钥
```

不应以明文保存在普通业务数据库中。

# 10.36 V3.0 数据库设计边界总结

认证中心数据库最终形成以下边界：

```text
┌─────────────────────────────────────────────┐
│              统一认证中心数据库              │
│                                             │
│ 用户身份                                     │
│ 组织机构                                     │
│ 用户任职                                     │
│ 主任职                                       │
│ 密码安全                                     │
│ 认证中心管理权限                             │
│ 登录日志                                     │
│ 审计日志                                     │
│ OAuth2/OIDC                                  │
│                                             │
└──────────────────────┬──────────────────────┘
                       │
                       │ OAuth2/OIDC/JWT
                       ▼
┌─────────────────────────────────────────────┐
│               各业务子系统                   │
│                                             │
│ 业务用户映射                                 │
│ 业务角色                                     │
│ 业务权限                                     │
│ 菜单/按钮                                    │
│ DataScope                                   │
│ 业务数据                                     │
└─────────────────────────────────────────────┘
```

因此，**统一认证中心数据库解决的是“你是谁、你属于哪里、你有哪些任职、你是否可以登录、你通过哪个 OAuth 客户端访问系统”**；而**“你在某个业务系统里能做什么、能看哪些业务数据”仍由业务系统自己决定**。

这也是 V3.0 数据库设计必须保持的核心边界。
