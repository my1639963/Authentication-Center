# 农牧业大数据平台——统一认证中心需求说明

**版本：V2.0**

---

# 一、项目概述

## 1.1 项目背景

农牧业大数据平台包含种植业、畜牧兽医、农田建设、农产品质量安全、市场信息等多个业务子系统。各业务系统在用户登录、身份认证等方面存在重复建设问题，需要建设统一认证中心，为平台内各业务系统提供统一的用户身份认证能力。

统一认证中心负责平台用户的统一身份管理和认证服务，实现“一次登录、多系统访问”，并通过标准 OAuth 2.0 / OpenID Connect 协议向各业务子系统提供标准化认证能力。

各业务子系统作为资源服务器，根据统一认证中心签发的访问令牌确认用户身份，并**独立维护本系统的角色、功能权限、业务权限和数据权限**。

统一认证中心不参与业务系统内部授权决策，不维护各业务系统的业务角色和数据权限规则。

---

## 1.2 建设目标

本项目主要实现以下目标：

1. 建立统一用户身份体系。
2. 建立统一组织机构、单位、部门和岗位基础信息。
3. 建立统一登录认证服务。
4. 支持 OAuth 2.0 / OpenID Connect 标准认证协议。
5. 支持 Authorization Code + PKCE 认证模式。
6. 支持 Client Credentials 系统间认证模式。
7. 支持 JWT Access Token。
8. 通过 JWKS 向业务子系统提供 JWT 签名公钥。
9. 实现集中认证、分散验证。
10. 支持统一登录和多业务系统单点登录。
11. 支持统一登录安全策略和认证审计。
12. 满足信创环境下的国产数据库、国产中间件和国产基础软件部署要求。
13. 最终生产环境不依赖 Docker 容器运行。
14. 各业务子系统保持独立授权能力，不强制采用统一权限模型。
15. 不提供业务子系统 SDK，各业务系统通过标准 OAuth/OIDC 协议接入。

---

# 二、系统职责边界

## 2.1 统一认证中心职责

统一认证中心负责：

* 用户身份管理；
* 用户账户管理；
* 用户登录认证；
* 密码管理；
* 登录安全控制；
* 单位管理；
* 部门管理；
* 行政区划基础信息管理；
* 岗位/职务基础信息管理；
* 用户与组织关系管理；
* OAuth 2.0 / OpenID Connect 服务；
* Access Token 签发；
* Refresh Token 管理；
* JWT 签名；
* JWKS 公钥发布；
* OAuth/OIDC 元数据发布；
* 客户端注册管理；
* 登录及认证审计；
* 密钥生命周期管理；
* 认证服务高可用。

---

## 2.2 统一认证中心不负责的内容

以下内容不纳入统一认证中心建设范围：

### 1. 业务系统角色

例如：

```text
畜牧管理员
养殖场管理员
兽医审核员
防疫审批员
```

由对应业务系统自行定义。

### 2. 业务功能权限

例如：

```text
livestock:create
livestock:update
livestock:approve
livestock:delete
```

由业务系统自行维护。

### 3. 业务数据权限

例如：

```text
只能查看本部门数据
只能查看本单位数据
只能查看本县数据
只能查看本市数据
只能查看全省数据
```

由业务系统自行设计和实现。

统一认证中心**不定义、不维护、不计算、不下发 `DataScope`**。

### 4. 业务授权决策

统一认证中心只回答：

> “这个用户是谁？”

业务系统负责回答：

> “这个用户在本系统中能做什么？”

# 四、架构原则

## 4.1 集中认证、分散授权

统一认证中心负责身份认证。

各业务子系统负责授权。

即：

```text
Authentication
       ↓
统一认证中心

Authorization
       ↓
各业务子系统
```

---

## 4.2 集中认证、分散验证

用户登录统一由认证中心完成。

业务系统获得 Access Token 后，在本地完成 JWT 验证，不要求每次业务请求都访问认证中心。

---

## 4.3 标准协议接入

业务系统必须通过标准协议与统一认证中心进行集成：

* OAuth 2.0；
* OpenID Connect；
* JWT；
* JWKS；
* OIDC Discovery。

不要求业务系统引用统一认证中心专用 SDK。

---

## 4.4 子系统授权独立

每个业务系统可以根据自身业务特点独立设计：

* 用户映射；
* 角色；
* 菜单；
* 按钮权限；
* API 权限；
* 数据权限；
* 审批权限；
* 业务规则。

统一认证中心不强制规定业务系统采用 RBAC、ABAC 或其他授权模型。

---

# 五、用户管理需求

## 5.1 用户账户管理

系统应支持：

* 用户创建；
* 用户修改；
* 用户启用；
* 用户禁用；
* 用户删除；
* 用户查询；
* 用户详情；
* 用户状态管理；
* 用户登录名管理。

用户登录名必须全局唯一。

---

## 5.2 用户基本信息

用户基础信息至少包括：

| 字段   | 说明                   |
| ---- | -------------------- |
| 用户ID | 系统唯一标识               |
| 登录名  | 用户登录账号               |
| 姓名   | 用户真实姓名               |
| 手机号  | 用户联系方式               |
| 邮箱   | 用户邮箱                 |
| 身份证号 | 实名认证信息，可按安全要求脱敏/加密存储 |
| 用户状态 | 正常、禁用、锁定等            |
| 创建时间 | 创建时间                 |
| 更新时间 | 更新时间                 |

---

## 5.3 密码管理

系统应支持：

* 设置密码；
* 修改密码；
* 管理员重置密码；
* 密码复杂度校验；
* 密码历史记录；
* 密码过期策略；
* 初始密码强制修改；
* 密码安全存储。

密码不得采用明文存储。

---

# 六、组织机构管理需求

## 6.1 行政区划管理

系统应支持省、市、县及下级行政区划基础信息维护。

行政区划与组织单位属于不同维度：

```text
行政区划
省
 └── 市
      └── 县
```

与：

```text
组织机构
单位
 └── 部门
      └── 岗位
```

两个体系独立维护。

---

## 6.2 单位管理

单位表示平台统一身份体系中的组织主体。

单位信息至少包括：

| 字段           | 说明     |
| ------------ | ------ |
| UnitId       | 单位ID   |
| UnitCode     | 单位编码   |
| UnitName     | 单位名称   |
| UnitType     | 单位类型   |
| UnitLevel    | 单位层级   |
| RegionId     | 所属行政区划 |
| ParentUnitId | 上级单位   |
| Status       | 单位状态   |
| Sort         | 排序     |

支持：

* 单位新增；
* 单位修改；
* 单位查询；
* 单位启用/停用；
* 单位层级维护；
* 单位上下级关系维护。

---

## 6.3 部门管理

部门属于单位内部组织机构。

支持：

* 部门新增；
* 部门修改；
* 部门删除；
* 部门查询；
* 部门层级维护；
* 部门负责人维护；
* 部门启用/停用。

部门必须归属于一个单位。

---

## 6.4 岗位/职务管理

统一认证中心维护基础岗位/职务信息，用于描述用户的组织身份。

例如：

```text
厅长
副厅长
处长
副处长
科长
副科长
科员
```

岗位信息属于用户身份基础信息。

**岗位/职级不直接等价于业务系统角色，也不直接决定业务系统数据权限。**

---

# 七、用户与组织关系

用户可以关联：

* 所属单位；
* 所属部门；
* 岗位/职务；
* 行政区划。

建议采用独立的用户组织关系模型，避免将组织关系全部固化在用户表中。

---

## 7.1 用户所属单位

原则上一个用户具有一个主单位。

---

## 7.2 用户所属部门

用户可以关联部门。

单位级人员可以不关联具体部门。

例如：

```text
农业农村厅
 ├── 种植业管理处
 │    ├── 张三
 │    └── 李四
 │
 ├── 畜牧兽医处
 │    ├── 王五
 │    └── 赵六
 │
 └── 厅领导
```

是否允许一个用户同时具有多个组织任职关系，应通过用户组织关系模型进行扩展，不在认证协议层面限制。

---

# 八、认证功能需求

## 8.1 单点登录

系统应支持：

> 一次登录，多系统访问。

用户完成统一认证后，可以访问已经授权的多个业务系统，而无需重复输入用户名和密码。

---

## 8.2 OAuth 2.0

统一认证中心提供标准 OAuth 2.0 服务。

支持：

### Authorization Code

主要用于：

* Web 应用；
* 管理平台；
* 移动端；
* 第三方用户登录。

Authorization Code 流程必须支持 PKCE。

---

### Client Credentials

用于系统间服务调用。

例如：

```text
业务系统A
    ↓
统一认证中心
    ↓
Access Token
    ↓
业务系统B
```

该模式不代表具体业务用户身份，而代表客户端/系统身份。

---

### Refresh Token

支持 Access Token 自动续期。

---

# 九、OpenID Connect

统一认证中心应支持 OpenID Connect。

提供：

```text
/.well-known/openid-configuration
```

用于发布认证服务元数据。

支持：

* UserInfo；
* ID Token；
* Discovery；
* JWKS；
* 标准 OIDC Claims。

---

# 十、Token 管理

## 10.1 Access Token

Access Token 推荐采用 JWT。

JWT 至少包含：

```json
{
  "iss": "https://auth.example.gov.cn",
  "sub": "10001",
  "aud": "livestock-api",
  "jti": "xxxxxxxx",
  "iat": 1790000000,
  "exp": 1790000600
}
```

必要时可以包含统一身份上下文，例如：

```json
{
  "sub": "10001",
  "username": "zhangsan",
  "unit_id": "100",
  "department_id": "200",
  "position_id": "10"
}
```

---

## 10.2 明确禁止下发的业务授权信息

统一认证中心不负责业务授权，因此 JWT 不要求包含：

```text
DataScope
Role
Permission
Menu
ButtonPermission
BusinessPermission
```

尤其不包含：

```json
{
  "data_scope": "DEPARTMENT"
}
```

业务角色及数据权限由各业务系统自行管理。

---

# 十一、Audience 设计

Access Token 的 `aud` 应表示目标资源服务器。

例如：

```text
aud = livestock-api
```

表示该 Token 用于访问畜牧业务 API。

不同业务系统应使用不同的 Audience：

```text
livestock-api
planting-api
fishery-api
farm-api
```

避免一个 Access Token 可以无约束访问所有业务系统。

---

# 十二、JWT/JWKS

## 12.1 JWT 签名

统一认证中心负责对 Access Token 进行签名。

建议采用非对称密钥。

---

## 12.2 JWKS

提供：

```text
/oauth2/jwks
```

业务系统通过 JWKS 获取签名公钥。

---

## 12.3 本地验证

业务系统：

```text
获取 JWKS
     ↓
缓存公钥
     ↓
收到 JWT
     ↓
验证签名
     ↓
验证 iss
     ↓
验证 aud
     ↓
验证 exp
     ↓
建立本地用户身份
```

不要求每次 API 请求都访问认证中心。

---

## 12.4 密钥轮换

系统必须支持 JWK 密钥轮换。

密钥轮换期间：

```text
旧公钥 + 新公钥
```

同时发布。

新旧公钥重叠有效时间不少于 **24 小时**。

---

# 十三、认证安全需求

## 13.1 登录失败控制

连续登录失败达到 5 次后：

```text
账户锁定 15 分钟
```

系统应记录：

* 登录账号；
* 登录时间；
* 登录 IP；
* 登录结果；
* 失败原因；
* 客户端信息。

---

## 13.2 HTTPS

生产环境所有认证接口必须使用 HTTPS。

禁止通过 HTTP 明文传输：

* 用户名；
* 密码；
* Authorization Code；
* Access Token；
* Refresh Token。

---

## 13.3 PKCE

Authorization Code 流程必须支持 PKCE。

---

## 13.4 Token 有效期

建议：

```text
Access Token：5～15分钟
Refresh Token：7～30天
```

具体有效期支持配置。

---

# 十四、客户端管理

统一认证中心应支持业务系统客户端注册。

每个业务系统建立独立 Client。

例如：

```text
livestock-web
livestock-api
planting-web
planting-api
fishery-web
fishery-api
```

客户端至少维护：

* ClientId；
* ClientSecret；
* ClientName；
* RedirectUri；
* AllowedGrantTypes；
* AllowedScopes；
* AllowedAudiences；
* ClientStatus。

---

# 十五、业务子系统接入需求

## 15.1 业务系统接入方式

业务系统不依赖统一认证中心 SDK。

采用：

```text
OAuth/OIDC
+
JWT
+
JWKS
```

进行标准化接入。

---

## 15.2 业务系统必须完成

每个业务系统负责：

1. JWT Token 验证；
2. Issuer 验证；
3. Audience 验证；
4. Token 有效期验证；
5. 本系统用户映射；
6. 本系统角色管理；
7. 本系统功能权限管理；
8. 本系统业务授权；
9. 本系统数据权限管理。

---

## 15.3 业务系统独立授权

例如畜牧系统：

```text
统一认证用户
       ↓
畜牧系统用户
       ↓
畜牧系统角色
       ↓
畜牧系统功能权限
       ↓
畜牧系统数据权限
```

种植系统可以采用完全不同的授权模型。

统一认证中心不干预。

---

# 十六、接口需求

## 16.1 OAuth 接口

统一认证中心至少提供：

| 接口                                  | 方法   | 说明             |
| ----------------------------------- | ---- | -------------- |
| `/oauth2/authorize`                 | GET  | 授权端点           |
| `/oauth2/token`                     | POST | Token 获取       |
| `/oauth2/revoke`                    | POST | Token 撤销       |
| `/oauth2/introspect`                | POST | Token 内省       |
| `/oauth2/jwks`                      | GET  | JWKS           |
| `/.well-known/openid-configuration` | GET  | OIDC Discovery |
| `/userinfo`                         | GET  | OIDC 用户信息      |

具体端点名称可根据实际 OAuth/OIDC 框架进行配置，但必须符合标准协议要求。

# 二十、明确排除的数据模型

统一认证中心数据库**不设计以下业务授权表**：

```text
业务角色表
业务权限表
业务菜单表
业务按钮权限表
业务数据权限表
DataScope
业务角色-权限关系
业务用户-角色关系
```

这些数据属于业务子系统。

例如：

```text
畜牧系统数据库
    livestock_role
    livestock_permission
    livestock_user_role
    livestock_data_permission
```

由畜牧系统自行设计。

# 二十一、信创要求

## 21.1 总体要求

系统必须满足项目指定信创环境要求。

生产环境数据库、中间件、操作系统等基础软件必须采用项目批准的国产化产品。

---

## 21.2 数据库

统一认证中心不得依赖特定国外数据库产品。

数据库访问层采用 EF Core 抽象。

最终根据项目实际信创目录选择国产数据库，例如：

```text
达梦
人大金仓
OceanBase
其他项目批准的国产数据库
```

具体产品以项目实际采购及兼容性测试结果为准。

---

## 21.3 中间件

生产环境中间件必须采用项目批准的国产中间件。

具体产品根据项目现有信创环境确定。

---

## 21.4 Docker

Docker 不作为生产环境部署基础设施。

生产部署采用：

```text
Linux
+
.NET Runtime
+
系统服务
+
国产中间件
+
国产数据库
```

可在开发、测试阶段使用 Docker 提高环境搭建效率，但最终生产环境不得以 Docker 作为运行前提。

---

# 二十二、部署与高可用

## 22.1 应用节点

认证中心至少部署两个应用节点：

```text
负载均衡
   │
   ├── 认证节点1
   │
   └── 认证节点2
```

支持水平扩展。

---

## 22.2 无状态设计

认证服务应用节点原则上保持无状态。

节点之间不保存无法共享的本地会话数据。

---

## 22.3 密钥共享

所有认证节点必须能够使用统一的签名密钥体系。

避免：

```text
节点1签发 Token
节点2无法验证
```

---

## 22.4 数据库高可用

认证中心核心数据采用项目批准的国产数据库高可用方案。

至少保证：

* 用户数据高可靠；
* 认证配置高可靠；
* OAuth 客户端数据高可靠；
* 事务一致性；
* 故障恢复。

---

# 二十三、缓存及临时状态

认证中心可以根据最终信创环境选择合适的国产缓存或中间件，用于：

* 登录失败次数；
* 登录锁定状态；
* 临时授权状态；
* 验证码；
* Session；
* 临时认证数据；
* 限流数据。

缓存并非用户核心数据唯一存储位置。

核心用户及认证配置数据必须持久化到数据库。

---

# 二十四、审计需求

系统必须记录认证相关审计日志。

至少包括：

### 登录审计

* 用户；
* 时间；
* IP；
* User-Agent；
* 登录结果；
* 失败原因。

### Token 审计

* ClientId；
* 用户；
* Token 签发时间；
* Token 类型；
* Token 撤销；
* Token 过期。

### 用户管理审计

* 创建用户；
* 修改用户；
* 禁用用户；
* 删除用户；
* 重置密码。

### 组织管理审计

* 单位变更；
* 部门变更；
* 用户组织关系变更；
* 岗位变更。

---

# 二十五、非功能需求

## 25.1 性能要求

认证接口：

> P95 响应时间 < 200ms

---

## 25.2 并发要求

认证服务器支持：

> ≥1000 个并发登录请求

具体容量通过压力测试进行验证。

---

## 25.3 JWT 验证

业务系统本地 JWT 验证，不依赖认证中心实时调用。

JWT 验证应满足业务系统自身性能要求，不因认证中心网络延迟影响正常业务请求。

---

## 25.4 可用性

认证中心应满足项目要求的高可用指标。

建议目标：

> 年度可用性 ≥ 99.9%

---

# 二十六、数据一致性要求

以下数据必须保证一致性：

* 用户账户；
* 用户状态；
* 单位；
* 部门；
* 用户组织关系；
* 岗位；
* OAuth 客户端；
* Token 及授权相关数据。

---

# 二十七、异常处理

系统至少处理：

* 用户不存在；
* 用户被禁用；
* 用户被锁定；
* 密码错误；
* Client 不存在；
* Client 无效；
* RedirectUri 不合法；
* Authorization Code 无效；
* Authorization Code 已使用；
* Token 已过期；
* Refresh Token 无效；
* Scope 不允许；
* Audience 不允许；
* JWT 签名验证失败；
* JWKS 获取失败。

---

# 二十八、系统安全边界

统一认证中心是平台的身份信任根之一。

因此：

```text
统一认证中心
       │
       ├── 用户身份
       ├── 登录状态
       ├── Token签发
       └── 签名密钥
```

必须重点保护。

业务系统：

```text
业务系统
       │
       ├── 角色
       ├── 功能权限
       ├── 数据权限
       └── 业务规则
```

独立负责授权。

# 三十、最终架构定位

本项目最终采用：

> **“统一身份、统一认证、标准协议、分散授权、分散验证”的总体架构。**

统一认证中心只负责建立可信的用户身份和认证体系，通过 OAuth 2.0 / OpenID Connect 向业务子系统提供标准身份认证服务。

各业务子系统通过 JWT/JWKS 完成本地身份验证，并根据自身业务特点独立建设角色、功能权限和数据权限体系。

统一认证中心不参与业务授权，不定义 DataScope，不要求业务系统使用统一 SDK，不要求各业务系统采用统一的 RBAC 或数据权限模型。

系统生产环境采用项目批准的国产操作系统、国产数据库、国产中间件等信创基础设施，Docker 仅可用于开发或测试环境，不作为生产环境部署依赖。

最终形成：

                  └──────────┬──────────┘
                             │

                        Access Token
                             │
       ┌─────────────────────┼─────────────────────┐
       │                     │                     │
       ▼                     ▼                     ▼
  ┌──────────┐          ┌──────────┐          ┌──────────┐
  │ 畜牧系统  │          │ 种植系统  │          │ 渔业系统  │
