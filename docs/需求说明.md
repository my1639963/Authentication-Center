# 1. 项目概述

## 1.1 建设背景

农牧业大数据平台包含种植业、畜牧兽医、农田建设、农产品质量安全、市场信息等多个业务子系统。各业务系统在用户登录、身份认证等方面存在重复建设问题，需要建设统一认证中心，为平台内各业务系统提供统一的用户身份认证能力。

统一认证中心负责平台用户的统一身份管理和认证服务，实现"一次登录、多系统访问"，并通过标准 OAuth 2.0 / OpenID Connect 协议向各业务子系统提供标准化认证能力。

各业务子系统作为资源服务器，根据统一认证中心签发的访问令牌确认用户身份，并独立维护本系统的角色、功能权限、业务权限和数据权限。

统一认证中心不参与业务系统内部授权决策，不维护各业务系统的业务角色和数据权限规则。

本文档定位为平台级公共认证服务的需求基线。后续详细设计、编码、测试和验收应以经评审确认的版本为准。

**合规声明**：本系统作为平台级身份信任根，其安全设计和实现应满足以下要求：

- GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》第三级要求；
- GB/T 39786-2021《信息安全技术 信息系统密码应用基本要求》第三级要求；
- 信息技术应用创新（信创）相关要求。

**责任边界声明**：本系统按平台整体等保方案和密码应用方案进行能力集成，本系统自身承担的需求由本系统实现；业务子系统承担其自身的角色、功能权限、业务权限与数据权限；传输通道密码保护、可信时间源、数据库与中间件基础设施由平台基础设施承担；最终等保测评对象、密评对象、测评范围和符合性以平台整体方案及正式测评结果为准。

最终定级以平台整体定级结果为准。

## 1.2 软件定位

统一认证中心（Authentication Center，以下简称"本系统"）定位为农牧业大数据平台统一的用户身份与认证基础服务。

核心原则：统一身份、统一认证，不统一业务授权。

本系统负责用户身份、组织基础信息、登录认证、令牌签发与验证公钥发布、认证审计；各业务子系统负责本系统的角色、功能权限、业务权限与数据权限。

本系统是平台的身份信任根之一。一旦身份签发环节被攻破，将影响所有接入业务系统，因此本系统必须重点保护用户身份、登录状态、令牌签发与签名密钥。

## 1.3 建设目标

总体目标是建立统一、安全、标准化、可审计的统一身份认证能力，为平台内各业务子系统提供统一身份认证基础设施。

### 1.3.1 统一用户身份与组织基础信息

1. 建立统一用户身份体系；
2. 建立统一组织机构、单位、部门和岗位基础信息；
3. 建立用户与组织关系，为业务系统提供可信的用户身份上下文。

### 1.3.2 统一登录认证与单点登录

1. 建立统一登录认证服务；
2. 支持统一登录和多业务系统单点登录，实现"一次登录、多系统访问"。

### 1.3.3 标准协议与令牌能力

1. 支持 OAuth 2.0 / OpenID Connect 标准认证协议；
2. 支持 Authorization Code + PKCE 认证模式；
3. 支持 Client Credentials 系统间认证模式；
4. 支持 JWT Access Token；
5. 通过 JWKS 向业务子系统提供 JWT 签名公钥；
6. 不提供业务子系统 SDK，各业务系统通过标准 OAuth/OIDC 协议接入。

### 1.3.4 集中认证、分散授权与分散验证

1. 实现集中认证、分散验证，业务系统本地完成 JWT 验证；
2. 各业务子系统保持独立授权能力，不强制采用统一权限模型；
3. 统一认证中心不参与业务授权决策，不定义、不维护、不计算、不下发 DataScope。

### 1.3.5 认证安全与审计

1. 支持统一登录安全策略，包括登录失败控制、锁定策略、令牌有效期策略；
2. 支持认证审计，覆盖登录、令牌、用户管理与组织管理操作。

### 1.3.6 合规与信创适配

1. 满足信创环境下的国产数据库、国产中间件和国产基础软件部署要求；
2. 最终生产环境不依赖 Docker 容器运行；
3. 满足等保三级对身份鉴别、访问控制、安全审计及剩余信息保护的要求；
4. 满足密评对身份鉴别密码技术、传输通道密码保护及审计完整性保护的要求。

16. OAuth/OIDC 元数据发布；

### 1.4.2 本期不包含

以下内容不纳入本系统建设范围：

- 业务系统角色，例如畜牧管理员、养殖场管理员、兽医审核员、防疫审批员，由对应业务系统自行定义；
- 业务功能权限，例如 `livestock:create`、`livestock:update`、`livestock:approve`、`livestock:delete`，由业务系统自行维护；
- 业务数据权限，例如只能查看本部门数据、只能查看本单位数据、只能查看本县数据、只能查看本市数据、只能查看全省数据，由业务系统自行设计和实现；
- 业务授权决策。本系统只回答"这个用户是谁？"，业务系统负责回答"这个用户在本系统中能做什么？"；
- 业务系统的用户映射、菜单、按钮权限、审批权限与业务规则；
- 业务子系统 SDK；
- 业务系统统一权限模型与统一 DataScope 模型；
- 业务系统的业务审计范围扩展。

本系统**不定义、不维护、不计算、不下发 `DataScope`**。

## 1.7 建设原则

### 1.7.1 集中认证、分散授权

统一认证中心负责身份认证，各业务子系统负责授权。

```text
Authentication
       ↓
统一认证中心

Authorization
       ↓
各业务子系统
```

### 1.7.2 集中认证、分散验证

用户登录统一由认证中心完成。业务系统获得 Access Token 后，在本地完成 JWT 验证，不要求每次业务请求都访问认证中心。

### 1.7.3 标准协议接入

业务系统必须通过标准协议与统一认证中心进行集成：

- OAuth 2.0；
- OpenID Connect；
- JWT；
- JWKS；
- OIDC Discovery。

不要求业务系统引用统一认证中心专用 SDK。

### 1.7.4 子系统授权独立

每个业务系统可以根据自身业务特点独立设计用户映射、角色、菜单、按钮权限、API 权限、数据权限、审批权限与业务规则。统一认证中心不强制规定业务系统采用 RBAC、ABAC 或其他授权模型。

### 1.7.5 无状态设计

认证服务应用节点原则上保持无状态，节点之间不保存无法共享的本地会话数据，可多实例部署并支持水平扩展。

### 1.7.6 最小权限

用户、客户端、服务账号及数据库账号仅授予完成职责所需的最小权限。Access Token 通过 `aud` 与 `scope` 约束可用范围。

### 1.7.7 全程审计

登录、登出、令牌签发、令牌撤销、用户管理、组织管理、密钥管理等关键操作均必须产生审计记录，审计日志通过完整性链防篡改。

### 1.7.8 等保与密评合规

系统设计和实现必须满足等保三级和密评三级要求。密码应用安全性评估应在系统投入运行前完成。

### 1.7.9 信创优先

在同等功能条件下，优先选择国产 CPU、国产操作系统、国产数据库、国产中间件与国产基础软件。信创组件选型应通过项目兼容性测试验证。Docker 不作为生产环境部署前提。

### 1.7.10 三员分立与互斥【待确认】

引入等保三级基线后，管理端应具备系统管理员、审计管理员、安全管理员职责分离与互斥能力。本系统原需求未定义管理端角色体系，是否在本期立项三员模型属合规基线引入的需求变更事项，详见 14.4 待确认事项清单。

### 1.7.11 责任边界清晰

本系统、业务子系统、数据库、缓存、基础设施各自承担明确的责任。详见第 13 章责任边界矩阵。

## 2.4 系统边界

系统角色：

| 角色                   | 系统           | 职责                            |
| ---------------------- | -------------- | ------------------------------- |
| Authorization Server   | 统一认证中心   | 用户认证、Token 签发、OIDC 服务 |
| Resource Server        | 各业务子系统   | JWT 验证、业务授权、业务数据权限 |
| Client                 | Web、移动端、业务系统 | 发起认证请求             |
| Identity Administrator | 统一认证管理端 | 用户及组织基础数据维护          |

本系统负责：

- 用户身份管理、用户账户管理、用户登录认证、密码管理；
- 登录安全控制与认证审计；
- 单位、部门、行政区划、岗位/职务基础信息管理；
- 用户与组织关系管理；
- OAuth 2.0 / OpenID Connect 服务；
- Access Token、Refresh Token、ID Token 的签发与撤销；
- JWT 签名、JWKS 公钥发布、OAuth/OIDC 元数据发布；
- 客户端注册管理；
- 签名密钥生命周期管理；
- 认证服务高可用与水平扩展。

本系统不负责：

- 业务系统角色、业务功能权限、业务菜单权限、业务数据权限与业务审批权限；
- 业务授权决策；
- DataScope 的定义、维护、计算与下发；
- 业务系统的用户映射与业务规则；
- 业务子系统 SDK；
- 业务系统的业务审计扩展范围；
- 数据库、缓存、操作系统、网络等基础设施运维。

统一认证中心与业务授权中心完全解耦。

## 3.7 Token 管理

### 3.7.1 Access Token

Access Token 推荐采用 JWT。

JWT 至少包含：

```json
{
  "iss": "https://auth.example.gov.cn",
  "sub": "10001",
  "aud": "livestock-api",
  "jti": "xxxxxxxx",
  "iat": 1790000000,
  "exp": 1790000600
}
```

必要时可以包含统一身份上下文，例如：

```json
{
  "sub": "10001",
  "username": "zhangsan",
  "unit_id": "100",
  "department_id": "200",
  "position_id": "10"
}
```

| 编号     | 功能          | 要求                       |
| -------- | ------------- | -------------------------- |
| F-TK-001 | Token 签发    | 签发 Access Token          |
| F-TK-002 | Token 校验    | 支持 Token 内省与校验      |
| F-TK-003 | Token 撤销    | 支持 Token 撤销            |
| F-TK-004 | Token 有效期  | 支持访问令牌有效期配置     |

### 3.7.2 明确禁止下发的业务授权信息

统一认证中心不负责业务授权，因此 JWT 不要求包含：

```text
DataScope
Role
Permission
Menu
ButtonPermission
BusinessPermission
```

尤其不包含：

```json
{
  "data_scope": "DEPARTMENT"
}
```

要求：业务角色及数据权限由各业务系统自行管理。

### 3.7.3 Audience 设计

Access Token 的 `aud` 应表示目标资源服务器。

例如：

```text
aud = livestock-api
```

表示该 Token 用于访问畜牧业务 API。

不同业务系统应使用不同的 Audience：

```text
livestock-api
planting-api
fishery-api
farm-api
```

要求：避免一个 Access Token 可以无约束访问所有业务系统。

业务系统通过 JWKS 获取签名公钥。

```text

     ↓

     ↓

     ↓

     ↓
验证 exp
     ↓

```

```text
旧公钥 + 新公钥
```

同时发布。

## 3.10 业务子系统接入

### 3.10.1 接入方式

业务系统不依赖统一认证中心 SDK。

采用：

```text
OAuth/OIDC
+
JWT
+
JWKS
```

进行标准化接入。

### 3.10.2 业务系统必须完成

每个业务系统负责：

1. JWT Token 验证；
2. Issuer 验证；
3. Audience 验证；
4. Token 有效期验证；
5. 本系统用户映射；
6. 本系统角色管理；
7. 本系统功能权限管理；
8. 本系统业务授权；
9. 本系统数据权限管理。

### 3.10.3 业务系统独立授权

例如畜牧系统：

```text
统一认证用户
       ↓
畜牧系统用户
       ↓
畜牧系统角色
       ↓
畜牧系统功能权限
       ↓
畜牧系统数据权限
```

种植系统可以采用完全不同的授权模型。统一认证中心不干预。

## 3.11 认证安全控制

### 3.11.1 登录失败控制

| 编号      | 功能             | 要求                             |
| --------- | ---------------- | -------------------------------- |
| F-SEC-001 | 登录失败计数     | 记录连续登录失败次数             |
| F-SEC-002 | 账户锁定         | 连续登录失败达到阈值后锁定账户   |
| F-SEC-003 | 自动解锁         | 锁定时间到期后自动解锁           |
| F-SEC-004 | 登录审计         | 记录登录账号、时间、IP、结果、失败原因、客户端信息 |

要求：

连续登录失败达到 5 次后：

```text
账户锁定 15 分钟
```

系统应记录：

- 登录账号；
- 登录时间；
- 登录 IP；
- 登录结果；
- 失败原因；
- 客户端信息。

### 3.11.2 HTTPS

生产环境所有认证接口必须使用 HTTPS。

禁止通过 HTTP 明文传输：

- 用户名；
- 密码；
- Authorization Code；
- Access Token；
- Refresh Token。

**【待确认】**：是否强制采用国密 TLS（GB/T 38636）替代通用 TLS，属密评基线引入的传输通道变更事项，详见 14.4 待确认事项清单。

### 3.11.3 PKCE

Authorization Code 流程必须支持 PKCE。

### 3.11.4 Token 有效期

建议：

```text
Access Token：5～15分钟
Refresh Token：7～30天
```

要求：具体有效期支持配置。

## 3.12 审计

**审计完整性链**：


## 3.13 异常处理

系统至少处理：

- 用户不存在；
- 用户被禁用；
- 用户被锁定；
- 密码错误；
- Client 不存在；
- Client 无效；
- RedirectUri 不合法；
- Authorization Code 无效；
- Authorization Code 已使用；
- Token 已过期；
- Refresh Token 无效；
- Scope 不允许；
- Audience 不允许；
- JWT 签名验证失败；
- JWKS 获取失败。

要求：

- 统一错误响应格式，返回明确错误码与 RequestId；
- 不得向外部返回堆栈、内部路径、SQL 语句、密钥材料等敏感信息；
- 认证类失败响应不得泄露用户是否存在等可用于枚举的信息。

## 5.6 部署与高可用

### 5.6.1 应用节点

认证中心至少部署两个应用节点：

```text
负载均衡
   │
   ├── 认证节点1
   │
   └── 认证节点2
```

要求：支持水平扩展。

### 5.6.2 无状态设计

认证服务应用节点原则上保持无状态，节点之间不保存无法共享的本地会话数据。

### 5.6.3 密钥共享

所有认证节点必须能够使用统一的签名密钥体系。

避免：

```text
节点1签发 Token
节点2无法验证
```

### 5.6.4 数据库高可用

认证中心核心数据采用项目批准的国产数据库高可用方案。

至少保证：

- 用户数据高可靠；
- 认证配置高可靠；
- OAuth 客户端数据高可靠；
- 事务一致性；
- 故障恢复。

## 5.7 网络环境

- 所有认证接口使用 HTTPS；
- 管理接口与认证接口隔离；
- 数据库不直接暴露公网；
- 管理网络限制访问来源；
- 支持 IP 白名单；
- 配置统一 NTP 时间源；
- 与各业务子系统网络互通。

## 5.8 信创兼容性矩阵

最终需形成完整矩阵：

| 类型       | 候选                     | 验证方式                |
| ---------- | ------------------------ | ----------------------- |
| CPU        | 海光/鲲鹏/飞腾/龙芯     | 项目兼容性测试          |
| OS         | 麒麟/统信/UOS/openEuler  | 项目兼容性测试          |
| DB         | 项目指定 P0 数据库       | EF Core Provider 验证   |
| .NET       | 实际运行时版本           | 项目兼容性测试          |
| 缓存       | 国产缓存/信创中间件      | 项目兼容性测试          |
| 中间件     | 项目批准的国产中间件     | 项目兼容性测试          |
| 密码模块   | 国产密码模块/密码服务    | 项目兼容性测试          |
| 浏览器     | Chrome/Edge/国产浏览器   | 兼容性测试              |
| Web Server | Nginx/国产 Web Server    | 兼容性测试              |

# 6. 接口规范

## 6.1 通用约定

HTTPS；JSON；UTF-8；ISO 8601；Authorization Bearer Token。

要求：

- 所有 API 必须返回 TraceId / RequestId；
- 管理类 API 统一前缀为 `/api/v1`；
- OAuth 2.0 / OIDC 标准端点路径遵循协议规范，不施加自定义版本前缀。

## 6.2 认证要求

业务 API：

```http
Authorization: Bearer {access_token}
```

OAuth 客户端认证：

```text
ClientId + ClientSecret（Client Credentials 模式）
ClientId + Authorization Code + PKCE（授权码模式）
```

要求：

- 客户端凭据不得出现在 URL 查询参数中；
- 认证失败必须记录审计。

## 6.3 请求与响应格式

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "requestId": "req-xxxx",
  "timestamp": "2026-09-23T10:30:00.000+08:00"
}
```

错误：

```json
{
  "code": 20001,
  "message": "invalid_grant",
  "data": null,
  "requestId": "req-xxxx",
  "timestamp": "2026-09-23T10:30:00.000+08:00"
}
```

不得向外部返回：

- 堆栈；
- 内部路径；
- SQL；
- 密码校验内部细节；
- 密钥材料；
- 可导致用户枚举的差异信息。

## 6.4 OAuth/OIDC 接口

统一认证中心至少提供：

| 接口                                | 方法 | 说明             |
| ----------------------------------- | ---- | ---------------- |
| `/oauth2/authorize`                 | GET  | 授权端点           |
| `/oauth2/token`                     | POST | Token 获取       |
| `/oauth2/revoke`                    | POST | Token 撤销       |
| `/oauth2/introspect`                | POST | Token 内省       |
| `/oauth2/jwks`                      | GET  | JWKS           |
| `/.well-known/openid-configuration` | GET  | OIDC Discovery |
| `/userinfo`                         | GET  | OIDC 用户信息      |

要求：具体端点名称可根据实际 OAuth/OIDC 框架进行配置，但必须符合标准协议要求。

## 6.5 用户管理接口

统一认证中心应提供用户管理 API：

```text
GET    /api/v1/users
GET    /api/v1/users/{id}
POST   /api/v1/users
PUT    /api/v1/users/{id}
DELETE /api/v1/users/{id}
POST   /api/v1/users/{id}/enable
POST   /api/v1/users/{id}/disable
POST   /api/v1/users/{id}/reset-password
```

## 6.6 组织管理接口

提供：

```text
/api/v1/units
/api/v1/departments
/api/v1/regions
/api/v1/positions
```

用于维护统一组织基础信息。

## 6.7 系统及健康检查接口

```text
GET /health
GET /live
GET /ready
GET /api/v1/system/info
```

## 6.8 幂等与防重放

以下操作必须支持幂等控制：

- Token 撤销；
- 客户端凭据重置；
- 用户启用/禁用；
- 密码重置。

建议支持：

```http
Idempotency-Key: xxx
```

涉及敏感操作的 API 必须支持：

- Timestamp；
- Nonce；
- 请求签名。

时间窗口由平台配置。

## 6.9 错误码

| 范围        | 类别       | 说明                                       |
| ----------- | ---------- | ------------------------------------------ |
| 10000-10099 | 认证       | 用户登录失败、密码错误、用户不存在/禁用/锁定 |
| 11000-11099 | Token      | Access Token、Refresh Token、ID Token 的签发、过期、撤销、校验失败 |
| 12000-12099 | 客户端     | Client 不存在、Client 无效、RedirectUri 不合法 |
| 13000-13099 | 授权       | Authorization Code 无效/已使用、Scope 不允许、Audience 不允许 |
| 20000-20099 | 参数       | 请求参数校验失败、字段缺失、格式错误       |
| 30000-30099 | 用户管理   | 用户创建、修改、删除、状态变更失败         |
| 40000-40099 | 组织管理   | 单位、部门、行政区划、岗位、用户组织关系操作失败 |
| 50000-50099 | 系统       | 内部错误、依赖服务不可用                   |
| 60000-60099 | 限流/配额  | QPS 超限、并发超限                         |
| 70000-70099 | JWKS/签名  | JWKS 获取失败、JWT 签名验证失败、密钥不可用 |
| 80000-80099 | 审计       | 审计写入失败、审计完整性校验失败           |

详细错误码分类与关键错误码示例见 14.3。

## 6.10 接口版本管理

管理类 API 使用：

```text
/api/v1/
```

后续重大不兼容变更使用：

```text
/api/v2/
```

要求：

- OAuth 2.0 / OIDC 标准端点遵循协议规范进行兼容性管理；
- V1 接口废弃必须提供废弃通知、迁移说明、兼容周期与新接口说明。

# 7. 数据需求

## 7.1 核心数据实体

至少包括：

1. 用户（sys_user）；
2. 用户组织关系（sys_user_organization）；
3. 单位（sys_unit）；
4. 部门（sys_department）；
5. 行政区划（sys_region）；
6. 岗位/职务（sys_position）；
7. OAuth 客户端；
8. 授权记录；
9. 授权范围（Scope）；
10. 令牌记录；
11. 审计日志；
12. 签名密钥与密钥版本；
13. 系统配置。

## 7.2 用户数据

用户数据主要存储：

```text
sys_user
```

至少包括：

| 字段       | 说明                                    |
| ---------- | --------------------------------------- |
| UserId     | 系统唯一标识                            |
| LoginName  | 登录名，全局唯一                        |
| RealName   | 姓名                                    |
| Mobile     | 手机号                                  |
| Email      | 邮箱                                    |
| IdCard     | 身份证号，脱敏/加密存储                 |
| Status     | 用户状态（正常、禁用、锁定）            |
| CreatedAt  | 创建时间                                |
| UpdatedAt  | 更新时间                                |

要求：

- IdCard 等敏感个人信息不得明文存储；
- 密码哈希、盐值与令牌签名材料等敏感数据单独管理，不与普通属性同表明文存储。

## 7.3 组织数据

组织数据主要存储：

```text
sys_unit
sys_department
sys_region
sys_position
```

要求：

- 行政区划与组织单位属于不同维度，独立维护；
- 单位、部门、岗位、行政区划的基础信息由其表结构承载，层级关系通过父级标识维护。

## 7.4 用户与组织关系数据

用户组织关系主要存储：

```text
sys_user_organization
```

要求：

- 建议采用独立的用户组织关系模型，避免将组织关系全部固化在用户表中；
- 原则上一个用户具有一个主单位；
- 单位级人员可以不关联具体部门；
- 是否允许一个用户同时具有多个组织任职关系，由该关系模型扩展支撑。

## 7.5 认证、客户端与授权数据

认证数据由 OAuth/OIDC 框架维护：

```text
OpenIddictApplications
OpenIddictAuthorizations
OpenIddictScopes
OpenIddictTokens
```

要求：

- 实际表结构根据最终采用的认证框架确定；
- 客户端凭据（ClientSecret）不得明文存储；
- 令牌与授权数据应支持按状态清理与按时间归档。

## 7.6 明确排除的数据模型

统一认证中心数据库**不设计以下业务授权表**：

```text
业务角色表
业务权限表
业务菜单表
业务按钮权限表
业务数据权限表
DataScope
业务角色-权限关系
业务用户-角色关系
```

这些数据属于业务子系统。例如：

```text
畜牧系统数据库
    livestock_role
    livestock_permission
    livestock_user_role
    livestock_data_permission
```

由畜牧系统自行设计。

## 7.7 数据完整性

以下数据必须具备完整性保护：

- 用户账户与用户状态；
- 用户组织关系；
- 单位、部门、行政区划、岗位；
- OAuth 客户端配置；
- 签名密钥元数据；
- 审计日志。

要求：

- 完整性保护机制应使用 SM3 或项目确定的其他密码技术；
- 完整性校验失败必须告警并记录安全事件。

## 7.8 数据保留

| 数据           | 保留                 |
| -------------- | -------------------- |
| 审计日志       | ≥6 个月，建议 3 年    |
| 用户数据       | 用户注销后按策略保留 |
| 组织数据       | 按组织变更策略保留   |
| 客户端数据     | 客户端注销后按策略保留 |
| 令牌与授权记录 | 过期后按策略清理     |
| 签名密钥       | 轮换后保留必要历史密钥 |

最终保留期限应以项目实际安全管理制度和验收要求为准。

## 7.9 数据备份

要求：

- 生产数据定期备份；
- 备份数据加密；
- 生产与备份环境隔离；
- 签名密钥相关数据必须重点保护；
- 审计日志独立归档；
- 备份结果必须记录；
- 备份失败必须告警。

## 7.10 数据恢复验证

仅"备份成功"不能作为恢复能力的验收依据。

必须定期进行：

```text
备份

恢复
 ↓
完整性验证
 ↓
登录认证验证
 ↓
令牌签发与验证验证
 ↓
数据一致性验证
 ↓
恢复结果记录
```

## 7.11 数据库权限

生产应用不得使用数据库超级账号。

至少区分：

- 应用账号；
- 数据库迁移账号；
- 运维账号；
- 审计只读账号。

要求：数据库账号遵循最小权限原则。

| 编号        | 需求                                                     |

| NF-DATA-001 | 审计日志表按时间分区，建议按月分区                       |

| NF-DATA-006 | 归档数据支持按需恢复和查询                               |

# 8. 安全需求

## 8.1 身份认证安全

用户：

- 登录名 + 密码；
- 登录失败控制与账户锁定；
- 密码复杂度与历史策略。

应用/客户端：

- ClientId + ClientSecret；
- Authorization Code + PKCE；
- Client Credentials。

要求：

- 生产环境所有认证接口必须使用 HTTPS；
- 禁止通过 HTTP 明文传输密码、授权码与令牌；
- 认证失败响应不得泄露可用于用户枚举的信息。

## 8.2 传输安全

- TLS 1.2 及以上；
- 根据实际部署支持国密 TLS【待确认】；
- 管理接口与认证接口隔离；
- 禁止明文传输密码、授权码与令牌。

## 8.3 权限控制

| 编号      | 功能             | 要求                         |
| --------- | ---------------- | ---------------------------- |
| F-AUTHZ-001 | 管理端登录认证 | 管理端独立登录               |
| F-AUTHZ-002 | 管理端权限控制 | 管理端功能按角色-权限矩阵控制 |
| F-AUTHZ-003 | 用户数据权限   | 用户与组织数据按管理范围约束  |

要求：

- 管理端应具备用户管理、组织管理、客户端管理、审计查询、系统配置等权限；
- 业务子系统的授权决策不在本系统范围内；
- 本系统不定义、不维护、不计算、不下发 DataScope。

## 8.4 管理员安全

管理员必须支持：

- 密码策略；
- 登录失败锁定；
- Session 超时；
- 高风险操作二次认证；
- 全量管理审计。

高风险操作至少包括：

- 客户端凭据重置；
- 签名密钥轮换；
- 权限与角色变更；
- 安全策略修改；
- 用户批量导入或删除。

## 8.5 Token 安全

Token 必须：

- 签名；
- 设置 exp；
- 设置 aud；
- 设置 iss；
- 设置 jti；
- 防止重放；
- 支持撤销；
- 不得写入普通业务日志。

要求：

- 不同业务系统应使用不同的 Audience；
- 避免一个 Access Token 可以无约束访问所有业务系统。

## 8.6 API 安全

API 必须支持：

- 参数校验；
- Body 大小限制；
- 字段长度限制；
- 限流；
- 防重放；
- 幂等；
- CORS 控制；
- Security Headers。

## 8.7 审计安全

审计日志：

- 追加写入；
- 不允许普通业务接口修改；
- 不允许普通管理员删除；
- 支持完整性验证；
- 支持独立归档；
- 支持定期备份。

## 8.8 日志安全

日志禁止包含：

- 用户密码；
- ClientSecret；
- 签名私钥；
- Access Token 完整内容；
- Refresh Token 完整内容；
- 身份证号等敏感个人信息明文。

必要时使用：

- 脱敏；
- 摘要；
- 长度；
- 标识。

## 8.9 密钥与签名安全

要求：

- 签名私钥不得明文存储；
- 签名私钥不得输出到日志或通过 API 返回；
- 所有认证节点必须能够使用统一的签名密钥体系；
- 支持 JWK 密钥轮换，新旧公钥重叠有效时间不少于 24 小时；
- 历史密钥保留与归档策略必须明确；
- 密钥管理操作必须记录审计。

## 8.10 密码技术应用与密评衔接

| 密码技术应用点   | 采用的密码技术                          | 责任方       |
| ---------------- | --------------------------------------- | ------------ |
| 身份鉴别         | 口令 + 密码技术（算法待详细设计确定）【待确认】 | 本系统 |
| 传输保护         | TLS（优先国密 TLS）                     | 本系统 + 基础设施 |
| 令牌签名         | 非对称签名（算法待详细设计确定）【待确认】 | 本系统     |
| 审计完整性保护   | SM3 哈希链 + SM2 签名                   | 本系统       |
| 敏感数据存储保护 | 加密 + 完整性保护                       | 本系统 + 数据库 |
| 数据备份保护     | 加密 + 完整性保护                       | 本系统 + 基础设施 |

要求：

- 本系统应能提供身份鉴别密码技术、令牌签名、审计完整性等环节的测评证据；
- 系统投入运行前应完成商用密码应用安全性评估；
- 最终密评范围与结论以平台整体方案及正式测评结果为准。

## 8.11 剩余信息保护

要求：

- 用户密码、ClientSecret、签名私钥、令牌等在内存中使用后应及时清零；
- 数据库记录删除后应通过数据库自身机制或应用层逻辑确保残留数据不可恢复；
- 缓存中不得长期保存敏感凭据与令牌材料。

**【待确认】**：本节为引入等保三级"剩余信息保护"要求后的新增安全需求，涉及功能与验收范围变更，暂不纳入本期需求基线，详见 14.4 待确认事项清单。

## 8.12 系统安全边界

统一认证中心是平台的身份信任根之一。因此：

```text
统一认证中心
       │
       ├── 用户身份
       ├── 登录状态
       ├── Token签发
       └── 签名密钥
```

必须重点保护。

业务系统：

```text
业务系统
       │
       ├── 角色
       ├── 功能权限
       ├── 数据权限
       └── 业务规则
```

独立负责授权。

# 12. 典型业务流程

## 12.1 授权码 + PKCE 单点登录

```text
用户访问业务系统
 ↓
业务系统生成 code_verifier 与 code_challenge
 ↓
业务系统重定向至统一认证中心 /oauth2/authorize
 ↓
统一认证中心判断用户是否已登录
 ↓
未登录：展示统一登录页，用户提交登录名与密码
 ↓
校验密码、用户状态、登录失败次数与锁定状态
 ↓
建立统一登录会话
 ↓
校验 ClientId、RedirectUri、Scope、Audience
 ↓
签发 Authorization Code 并重定向回业务系统
 ↓
业务系统携带 Code 与 code_verifier 请求 /oauth2/token
 ↓
统一认证中心校验 PKCE、Code 有效性与一次性
 ↓
签发 Access Token（JWT）与 Refresh Token
 ↓
业务系统本地验证 JWT 签名、iss、aud、exp
 ↓
建立本地用户身份并按本地授权模型授权
 ↓
记录登录审计与令牌审计
```

## 12.2 Client Credentials 系统间调用

```text
业务系统A 以 ClientId/ClientSecret 调用 /oauth2/token
 ↓
统一认证中心校验客户端凭据与授权类型
 ↓
校验 Scope 与 Audience
 ↓
签发代表客户端身份的 Access Token（不包含业务用户身份）
 ↓
业务系统A 携带 Token 调用业务系统B
 ↓
业务系统B 本地验证 JWT（签名、iss、aud、exp）
 ↓
业务系统B 按本地策略授权
 ↓
记录令牌审计
```

## 12.3 令牌刷新与撤销

```text
Access Token 即将过期
 ↓
业务系统使用 Refresh Token 请求 /oauth2/token
 ↓
统一认证中心校验 Refresh Token 有效性与未被撤销
 ↓
签发新的 Access Token（按策略轮换 Refresh Token）
 ↓
（撤销场景）业务系统或管理端请求 /oauth2/revoke
 ↓
统一认证中心将令牌标记为已撤销
 ↓
后续校验与内省返回未通过
 ↓
记录令牌审计
```

## 12.4 JWT 本地验证

```text
业务系统获取 JWKS
 ↓
缓存公钥
 ↓
收到 JWT
 ↓
验证签名
 ↓
验证 iss
 ↓
验证 aud
 ↓
验证 exp
 ↓
建立本地用户身份
 ↓
按业务系统本地角色与权限模型授权
```

要求：不要求每次 API 请求都访问认证中心。

## 12.5 JWKS 密钥轮换

```text
管理端发起签名密钥轮换
 ↓
生成新密钥对并入库
 ↓
JWKS 同时发布旧公钥与新公钥
 ↓
新签发令牌使用新密钥签名
 ↓
旧公钥保留用于验证存量令牌
 ↓
重叠有效时间不少于 24 小时
 ↓
存量令牌全部过期后旧公钥按策略归档
 ↓
记录密钥管理审计
```

## 12.6 用户与组织基础信息维护

```text
身份管理员登录管理端
 ↓
维护行政区划基础信息
 ↓
维护单位信息与单位层级
 ↓
维护部门信息、层级与负责人
 ↓
维护岗位/职务基础信息
 ↓
创建或维护用户账户与用户基本信息
 ↓
建立用户与单位、部门、岗位、行政区划的关系
 ↓
记录用户管理审计与组织管理审计
```

## 12.7 客户端接入与凭据分配

```text
业务系统对接方提出接入申请
 ↓
管理员注册客户端，分配 ClientId/ClientSecret
 ↓
配置 RedirectUri、AllowedGrantTypes、AllowedScopes、AllowedAudiences
 ↓
线下安全传递客户端凭据
 ↓
业务系统按 OAuth/OIDC 标准协议接入
 ↓
业务系统实现 JWT 本地验证与本系统用户映射
 ↓
业务系统独立建设角色、功能权限与数据权限
 ↓
（到期或泄露场景）轮换或撤销客户端凭据
 ↓
记录客户端管理审计
```

## 12.8 登录失败与账户锁定

```text
用户提交登录请求
 ↓
校验登录名与密码
 ↓
失败：登录失败次数累加
 ↓
记录登录审计（账号、时间、IP、结果、失败原因、客户端信息）
 ↓
达到阈值（连续 5 次）
 ↓
账户锁定 15 分钟
 ↓
锁定期间拒绝登录
 ↓
锁定期满自动解锁
 ↓
成功登录后清零失败计数
```
