# 1. 概述

## 1.1 编写目的

本文档为农牧业大数据平台统一认证中心 V3.0 详细设计文档，用于指导系统开发、测试、部署、验收及后续运维工作。

本文档对统一认证中心的系统架构、身份模型、组织模型、OAuth2.0/OIDC 协议、JWT Token、SSO、密钥管理、数据库、接口、安全、信创部署、性能、测试及灾备进行详细设计。

V3.0 在 V2.0 基础上进一步明确认证中心与业务子系统之间的职责边界，并针对国产数据库兼容性、多节点会话共享、管理员权限、Token 失效、多任职、国密、审计完整性等问题进行重新设计。

---

## 1.2 项目背景

农牧业大数据平台包含多个业务子系统，各系统均需要对用户身份进行认证。

随着业务系统数量增加，如果各业务系统独立维护账号和登录体系，将造成：

1. 用户账号重复建设；
2. 用户密码重复维护；
3. 登录入口不统一；
4. 用户组织信息不一致；
5. 用户离职、禁用后难以及时同步；
6. 多系统重复登录；
7. 安全审计分散；
8. 系统间认证机制不统一。

因此建设统一认证中心，对平台用户身份、组织身份及统一认证过程进行集中管理。

统一认证中心采用 OAuth2.0、OpenID Connect 等标准协议，为各业务系统提供统一身份认证服务。

## 1.4 设计原则

### 1.4.1 统一身份

认证中心统一维护平台级用户身份。

### 1.4.2 统一认证

所有业务系统通过统一认证中心完成用户身份认证。

### 1.4.3 标准协议

业务系统通过 OAuth2.0/OIDC 标准协议接入。

认证中心不提供业务 SDK，不要求业务系统依赖认证中心专用 SDK。

### 1.4.4 分散授权

业务角色、业务权限、菜单权限、按钮权限及 DataScope 均由业务系统自行维护。

认证中心不建设业务授权模型。

### 1.4.5 分散验证

业务系统作为 Resource Server，本地验证 JWT。

业务 API 正常请求不要求每次访问认证中心。

### 1.4.6 无状态应用

认证应用节点尽可能保持无状态，Session、OAuth 状态等共享数据放置于统一缓存或持久化存储。

### 1.4.7 信创优先

生产环境采用国产操作系统、国产数据库、国产缓存及符合要求的密码产品。

### 1.4.8 数据库可替换

业务领域模型不得绑定某一种数据库。

数据库 Provider 差异集中在 Infrastructure 层。

### 1.4.9 安全最小权限

认证中心只授予用户完成当前操作所需要的最低权限。

## 1.5 系统边界

认证中心负责：

```text
用户身份
    │
    ├── 用户账号
    ├── 用户密码
    ├── 用户状态
    ├── 组织关系
    ├── 任职信息
    └── 身份认证
          │
          ├── OAuth2
          ├── OIDC
          ├── JWT
          └── SSO
```

业务系统负责：

```text
业务系统
    │
    ├── 业务角色
    ├── 业务权限
    ├── 菜单权限
    ├── 按钮权限
    ├── 数据权限
    └── DataScope
```

认证中心禁止建设以下业务授权数据：

- 业务角色；
- 业务权限；
- 菜单；
- 按钮；
- DataScope；
- 用户与业务角色关联；
- 业务数据范围。

# 2. 总体架构

## 2.1 总体架构

系统采用：

**表示层 + 应用层 + 领域层 + 基础设施层 + OpenIddict 协议层**

架构如下：

```text
                    ┌─────────────────────┐
                    │      用户/浏览器      │
                    └──────────┬──────────┘
                               │ HTTPS
                               ▼
                    ┌─────────────────────┐
                    │       Nginx         │
                    │   HTTPS / 负载均衡   │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        ┌──────────┐     ┌──────────┐     ┌──────────┐
        │ Auth Node1│     │ Auth Node2│     │ Auth Node3│
        └─────┬────┘     └─────┬────┘     └─────┬────┘
              │                │                │
              └────────────────┼────────────────┘
                               │
             ┌─────────────────┴─────────────────┐
             │                                   │
             ▼                                   ▼
      国产数据库集群                       国产缓存集群
             │                                   │
             │                                   │
             └─────────────────┬─────────────────┘
                               │
                               ▼
                       密码服务/HSM
```

## 2.7 高可用架构

认证应用至少部署两个节点。

```text
                    Nginx
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
      Auth Node1              Auth Node2
          │                       │
          └───────────┬───────────┘
                      ▼
                Cache Cluster
                      │
                      ▼
                DB Cluster
```

要求：

1. 应用节点无状态；
2. Session 共享；
3. OAuth 数据共享；
4. 密钥一致；
5. 数据库高可用；
6. 缓存高可用；
7. Nginx 健康检查。

## 2.8 核心业务流程

### 2.8.1 SSO 登录流程

```text
业务系统
   │
   │ 未登录
   ▼
/oauth2/authorize
   │
   ▼
认证中心
   │
   ├── Session 已存在 ──────┐
   │                         │
   └── Session 不存在        │
            │                │
            ▼                │
         登录页面             │
            │                │
            ▼                │
       用户名/密码            │
            │                │
            ▼                │
       身份认证成功           │
            │                │
            ▼                │
        建立 SSO Session      │
            │                │
            └───────┬────────┘
                    ▼
             Authorization Code
                    │
                    ▼
              业务系统 Callback
                    │
                    ▼
               /oauth2/token
                    │
                    ▼
          Access Token / ID Token
                    │
                    ▼
            业务系统本地验证 JWT
```

V2.0 已明确业务接口请求不回调用认证中心进行 Token 校验，而由业务系统本地完成 JWT 校验；V3.0 保留该设计。

# 3. 身份与组织模型

## 3.1 用户身份模型

用户为认证中心最基本的身份主体。

用户包含：

- 登录名；
- 姓名；
- 手机号；
- 邮箱；
- 身份证号；
- 密码；
- 状态；
- 安全版本；
- 登录失败次数；
- 锁定时间。

---

## 3.2 行政区划模型

行政区划独立于组织机构。

支持：

```text
省
 └── 市
      └── 县
           └── 其他扩展层级
```

region_level 不硬编码为固定三级。

---

## 3.3 单位模型

单位形成组织树。

```text
省级单位
 ├── 市级单位
 │    ├── 部门
 │    └── 部门
 └── 市级单位
```

单位编码全局唯一。

---

## 3.4 部门模型

部门必须归属单位。

支持部门内部层级：

```text
单位
 ├── 办公室
 ├── 财务处
 └── 信息中心
       ├── 综合科
       └── 技术科
```

---

## 3.5 岗位/职务模型

岗位/职务属于身份组织元数据。

例如：

- 局长；
- 副局长；
- 处长；
- 副处长；
- 科长；
- 科员。

**岗位/职务不自动转换为业务权限。**

---

## 3.6 用户任职模型

用户与组织采用多对多关系。

```text
用户
 │
 ├── 任职1 → 单位A → 部门A → 职务A
 │
 ├── 任职2 → 单位B → 部门B → 职务B
 │
 └── 任职3 → 单位C → 部门C → 职务C
```

---

## 3.7 主任职模型

V3.0 不依赖：

```text
sys_user_organization.is_main = 1
```

来单独保证数据库层面的主任职唯一性。

增加：

`sys_user_main_organization`

用于保存用户唯一主任职关系。

核心约束：

```text
UNIQUE(user_id)
```

即一个用户只能存在一个主任职。

---

## 3.8 多任职模型

`sys_user_organization` 保存全部有效任职。

主任职由 `sys_user_main_organization` 独立管理。

JWT 只携带当前签发时的主任职信息：

```json
{
  "unit_id": "100",
  "department_id": "200",
  "position_id": "10"
}
```

这些字段表示：

> 当前 Token 对应的主任职。

不表示用户全部任职。

如业务系统需要完整任职信息，应通过：

- OIDC UserInfo；
- 或独立只读组织信息接口；

获取。

该接口必须通过 OAuth Scope 进行控制，例如：

```text
organization.read
```

业务系统不得通过 `/api/users` 管理接口获取用户兼职信息。

---

## 3.9 身份与业务授权边界

认证中心输出：

```text
sub
username
name
unit_id
department_id
position_id
```

认证中心不输出：

```text
role
permission
menu
button
data_scope
```

业务系统收到 JWT 后自行完成：

```text
JWT
 │
 ├── 用户身份
 ├── 单位
 ├── 部门
 └── 岗位/职务
       │
       ▼
业务系统自己的授权模型
       │
       ├── Role
       ├── Permission
       └── DataScope
```

---

# 4. 认证中心管理权限

## 4.1 管理权限设计原则

认证中心虽然不负责业务系统授权，但自身管理功能必须具备权限控制。

该权限仅用于：

> 谁可以管理认证中心本身。

例如：

- 用户管理；
- 组织管理；
- OAuth Client 管理；
- 审计查询；
- 安全策略配置。

---

## 4.2 管理角色

## 4.3 管理权限

建议权限：

## 4.4 管理角色与权限关系

采用标准 RBAC：

```text
管理员用户
     │
     ▼
sys_admin_user_role
     │
     ▼

     │
     ▼
sys_admin_role_permission
     │
     ▼
sys_admin_permission
```

---

## 4.5 管理员授权

管理员本身属于统一认证中心用户。

管理员权限只影响：

```text
/api/*
```

等认证中心管理 API。

不影响业务系统授权。

---

## 4.6 管理接口访问控制

管理 API 必须同时满足：

1. Token 有效；
2. issuer 正确；
3. audience 正确；
4. 用户有效；
5. 管理角色有效；
6. 管理权限满足。

例如：

```text
GET /api/users
```

要求：

```text
USER_VIEW
```

而：

```text
POST /api/users
```

要求：

```text
USER_CREATE
```

# 5. OAuth2.0 / OpenID Connect 详细设计

## 5.1 OAuth2.0 总体设计

认证中心使用 OpenIddict 实现 OAuth2/OIDC 协议。

业务代码不自行实现：

- Authorization Code；
- Token；
- Refresh Token；
- Client Credential；
- Consent；
- Token Revocation。

---

## 5.2 OpenID Connect 设计

OIDC 用于解决：

> 用户是谁？

OAuth2 解决：

> 客户端是否可以访问资源？

OIDC 在 OAuth2 基础上增加身份层。

---

## 5.3 Authorization Code + PKCE

Web 应用推荐：

```text
Authorization Code + PKCE
```

请求：

```text
GET /oauth2/authorize
```

核心参数：

```text
client_id
redirect_uri
response_type=code
scope=openid
state
code_challenge
code_challenge_method=S256
```

认证中心验证：

1. Client；
2. redirect_uri；
3. scope；
4. PKCE；
5. 用户 Session。

成功后生成 Authorization Code。

---

## 5.4 Client Credentials

用于：

```text
系统 → 系统
```

不代表具体用户。

例如：

```text
业务系统A
      │
      ▼
Client Credentials
      │
      ▼
认证中心
      │
      ▼
Access Token
```

该模式不得伪造用户身份。

---

## 5.5 Refresh Token

Refresh Token 用于 Access Token 续期。

V3.0 使用 Refresh Token Rotation：

```text
Refresh Token A
      │
      ▼
使用成功
      │
      ▼
Refresh Token B
```

A 立即失效。

如果再次使用 A：

```text
检测 Token Reuse
       │
       ▼
撤销整个 Token Family
```

---

## 5.6 OAuth Client 管理

Client 管理不得直接 CRUD OpenIddict 数据表。

通过 OpenIddict：

```text
ApplicationManager
ScopeManager
AuthorizationManager
TokenManager
```

等管理接口完成。

映射：

| 业务字段 | OpenIddict |
|---|---|
| client_id | ClientId |
| client_secret | ClientSecret |
| redirect_uri | RedirectUris |
| grant_type | Permissions |
| scope | Scopes |
| endpoint | Endpoint Permissions |

禁止业务代码直接修改：

```text
OpenIddictApplications
OpenIddictAuthorizations
OpenIddictScopes
OpenIddictTokens
```

---

## 5.7 Scope 管理

认证中心 Scope 分为：

### 身份 Scope

```text
openid
profile
email
```

### 组织信息 Scope

```text
organization.read
```

### 业务资源 Scope

由业务系统根据实际资源模型申请。

认证中心不在 Scope 中实现业务 DataScope。

---

## 5.8 Resource 与 Audience

必须区分：

### ClientId

表示：

> 哪个 OAuth 客户端申请 Token。

### Resource

表示：

> Token 请求访问哪个资源服务器。

### Audience

表示：

> Token 最终允许访问哪个资源/API。

例如：

```text
client_id = agriculture-web
resource = agriculture-api
```

认证中心根据标准资源配置最终生成：

```json
{
  "aud": "agriculture-api"
}
```

业务系统不得将 `aud` 当作普通自定义参数随意传入。

---

## 5.9 OpenIddict 集成

OpenIddict 负责 OAuth/OIDC 协议。

认证中心业务代码负责：

```text
用户
组织
安全策略
管理权限
审计
```

OpenIddict 负责：

```text
Authorization
Token
Client
Scope
OIDC
OAuth
```

两者边界必须保持清晰。

---

## 5.10 OAuth 标准错误处理

OAuth/OIDC 标准接口不得使用普通业务接口：

```json
{
  "code": 50001,
  "msg": "xxx"
}
```

而应按照协议返回：

```text
invalid_client
invalid_grant
invalid_request
invalid_scope
unauthorized_client
access_denied
unsupported_grant_type
```

---

## 5.11 Logout / End Session

V3.0 增加统一注销能力。

支持 OIDC End Session / RP-Initiated Logout 机制。

典型流程：

```text
业务系统
   │
   ▼
认证中心 Logout
   │
   ├── 清除 SSO Session
   │
   └── 返回业务系统
          │
          ▼
    业务系统清除本地 Session
```

Logout 不等同于业务系统自己的本地 Session 清理。

---

# 6. Token 详细设计

## 6.1 Access Token

Access Token 采用 JWT。

建议：

```text
Access Token TTL = 10 分钟
```

最终时间根据安全等级及甲方要求配置。

---

## 6.2 Refresh Token

Refresh Token 用于长期会话续期。

应：

- 服务端持久化；
- 支持撤销；
- 支持 Rotation；
- 支持 Token Family；
- 支持安全事件批量失效。

---

## 6.3 ID Token

ID Token 用于 OIDC 客户端确认用户身份。

包含：

```text
sub
iss
aud
iat
exp
nonce
name
preferred_username
```

不包含业务权限。

---

## 6.4 JWT Claims

建议：

```json
{
  "iss": "https://auth.example.gov.cn",
  "sub": "100001",
  "aud": "agriculture-api",
  "exp": 1780000000,
  "iat": 1779999400,
  "jti": "xxx",
  "username": "zhangsan",
  "name": "张三",
  "unit_id": "100",
  "department_id": "200",
  "position_id": "10",
  "token_version": 3
}
```

禁止：

```text
roles
permissions
data_scope
```

---

## 6.5 Audience 设计

业务 API 本地验证：

```text
signature
iss
aud
exp
nbf
```

业务系统只有发现：

```text
aud == 当前 API Resource
```

时才接受 Token。

---

## 6.6 Token Version

`sys_user.token_version` 用于处理用户安全事件。

安全事件包括：

- 禁用用户；
- 重置密码；
- 修改关键身份信息；
- 强制退出；
- 检测到安全风险。

执行：

```text
token_version++
```

同时：

```text
撤销 Refresh Token
```

---

## 6.7 普通安全失效模式

正常模式：

```text
安全事件
   │
   ├── token_version++
   │
   ├── revoke refresh token
   │
   └── Access Token 自然过期
```

由于 Access Token TTL 为短周期，旧 Token 的有效时间受到限制。

例如 TTL 为 10 分钟，则安全事件发生后旧 Token 最长约在剩余 TTL 内失效。

业务 API 不需要每次请求访问认证中心。

---

## 6.8 高安全失效模式

对于高安全业务：

```text
业务 API
   │
   ▼
Introspection
```

或采用：

```text
用户安全版本同步
```

进行更严格实时失效。

但不建议普通业务 API 每次请求都 Introspection。

---

## 6.9 Refresh Token Rotation

流程：

```text
RT-A
 │
 ▼
Token Endpoint
 │
 ├── Access Token
 │
 └── RT-B
```

RT-A 立即失效。

再次使用 RT-A：

```text
Token Reuse
   │
   ▼
Revoke Token Family
```

---

## 6.10 Token 撤销

支持：

```text
POST /oauth2/revoke
```

用于主动撤销 Token。

用户禁用、密码重置等安全事件必须同时处理 Refresh Token。

---

# 7. 密钥、JWT 与 JWKS 设计

## 7.1 密钥体系

认证中心使用非对称密钥签署 JWT。

结构：

```text
Private Key
    │
    ▼
JWT Sign
    │
    ▼
Access Token
```

业务系统只需要：

```text
Public Key
```

完成验证。

---

## 7.2 JWK

每个签名密钥具有：

```text
kid
kty
alg
use
n/e 或其他公钥参数
```

---

## 7.3 JWKS

统一认证中心：

```text
/oauth2/jwks
```

发布当前及轮换期间需要保留的公钥。

业务系统缓存 JWKS。

---

## 7.4 密钥生命周期

状态：

```text
PREPARE
ACTIVE
RETIRED
REVOKED
```

生命周期：

```text
PREPARE
   │
   ▼
ACTIVE
   │
   ▼
RETIRED
   │
   ▼
删除/归档
```

REVOKED 表示密钥发生安全问题，应立即停止使用。

---

## 7.5 密钥轮换

采用双 Key 重叠策略：

```text
旧 Key ────────────────┐
                       │
新 Key ────────┐       │
               │       │
               ▼       ▼
             JWKS 同时发布
```

旧 Key 与新 Key 至少保持必要的重叠周期。

建议重叠时间不少于 24 小时，具体根据 Token TTL、业务系统 JWKS 缓存周期确定。

---

## 7.6 私钥安全存储

生产环境：

**禁止明文保存 JWT 私钥。**

优先：

```text
HSM / 密码设备
```

其次：

```text
受保护的密钥存储
```

数据库不得保存明文私钥。

---

## 7.7 国密适配设计

V3.0 增加密码服务抽象层：

```text
认证业务
    │
    ▼
ICryptoProvider
    │
    ├── Software Provider
    │
    ├── 国密 Provider
    │
    └── HSM / 密码设备
```

认证中心不直接将：

```text
SM2
SM3
SM4
```

硬编码到业务领域层。

具体算法以：

- 密评要求；
- 密码应用方案；
- 实际密码设备能力；
- OpenIddict/JWT 实际适配验证结果；

为准。

不能在未完成实际验证前声称 OpenIddict 原生即可完成全部国密 JWT 能力。

---

## 7.8 业务系统公钥缓存

业务系统：

```text
启动
 │
 ▼
获取 JWKS
 │
 ▼
本地缓存
 │
 ▼
JWT 本地验证
```

发现：

```text
kid 不存在
```

时重新获取 JWKS。

---

# 8. SSO 单点登录设计

## 8.1 SSO 总体流程

SSO Session 保存：

```text
session_id
user_id
login_time
expire_time
client_context
security_context
```

---

## 8.2 SSO Session

Session 不保存在单个应用节点内存。

统一存储：

```text
国产缓存集群
```

必要的关键状态持久化到数据库。

---

## 8.3 多节点 Session 共享

```text
               Nginx
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      Node1    Node2    Node3
        │        │        │
        └────────┼────────┘
                 ▼
           Cache Cluster
```

任何节点都可以读取用户 Session。

---

## 8.4 Session 生命周期

建议：

```text
空闲超时：30 分钟
绝对超时：8 小时
```

最终值根据安全策略配置。

Session 过期后必须重新认证。

---

## 8.5 Session 故障降级

缓存故障时：

### 不允许

直接导致所有已有 JWT 全部失效。

### 允许

- 新建 Session 受限；
- 高风险登录暂时拒绝；
- 必要情况下查询数据库持久化状态；
- 告警。

已有 Access Token 仍按照 JWT 本地验证规则工作。

---

## 8.6 单点注销

注销：

```text
清除认证中心 Session
        │
        ▼
业务系统清理本地 Session
```

如果属于安全退出，可进一步：

```text
revoke refresh token
```

---

## 8.7 SSO 与 JWT 的关系

两者不是同一个概念：

```text
SSO Session
    │
    └── 管理“用户是否在认证中心登录”

JWT
    │
    └── 管理“业务 API 是否接受当前访问凭证”
```

业务 API 正常情况下不依赖 SSO Session。

---

# 9. 用户与组织管理

## 9.1 用户管理

支持：

- 新增；
- 修改；
- 查询；
- 启用；
- 禁用；
- 删除；

## 9.2 区域管理

支持：

- 新增；
- 修改；
- 查询；
- 停用；

已被单位引用的区域原则上不允许物理删除。

## 9.3 单位管理

```text
UNIQUE(unit_code)
```

单位删除优先采用停用。

## 9.4 部门管理

部门编码：

```text
UNIQUE(unit_id, dept_code)
```

## 9.5 岗位/职务管理

建议字段：

```text
position_code
position_name
position_type
position_level
status
sort
description
```

岗位/职务编码全局唯一。

---

## 9.6 用户任职管理

字段：

```text
user_id
unit_id
department_id（可空，单位级人员可不关联具体部门）
position_id（可空）
region_id（可空）
start_time
end_time
status
```

支持任职历史。

主任职由 `sys_user_main_organization` 独立管理。

## 9.7 多任职管理

支持：

```text
主任职

历史任职
```

## 9.8 用户状态管理

状态：

```text
正常
禁用
锁定
```

```text
status = DISABLED

revoke refresh tokens
```

---

## 9.9 密码生命周期管理

支持：

- 密码复杂度；
- 密码历史；
- 密码过期；
- 强制修改；
- 管理员重置；
- 用户主动修改。

密码只存：

```text
password_hash
```

禁止明文存储。

# 10. 数据库详细设计

## 10.1 数据库设计原则

数据库设计要求：

1. 不使用 MySQL 专有语法；
2. 不依赖 MySQL 特有数据类型；
3. JSON 内容使用跨数据库兼容文本类型；
4. 时间字段使用标准时间类型；
5. 主键使用 bigint；
6. 索引设计兼顾国产数据库；
7. 数据库差异集中在 EF Core Provider；
8. 业务领域层不依赖具体数据库。

---

## 10.2 sys_user 用户表

| 字段 | 类型 | 说明 |
|---|---|---|

# 12. 安全详细设计

## 12.1 身份安全

登录必须校验：

```text
账号存在
账号状态
密码
锁定状态
登录策略
```

---

## 12.2 密码安全

密码：

```text
不可逆 Hash
```

禁止：

```text
明文
可逆普通加密
```

密码必须满足复杂度策略。

---

## 12.3 登录安全

建议：

```text
连续失败 5 次
        │
        ▼
锁定 15 分钟
```

登录失败计数优先使用国产缓存。

缓存不可用时，可降级到数据库计数及事务控制。

不能因为缓存故障直接取消账户锁定机制。

---

## 12.4 Token 安全

必须验证：

```text
iss
aud
exp
nbf
signature
```

禁止：

```text
只解析 JWT Payload
```

不验证签名。

---

## 12.5 TLS 安全

所有对外认证接口：

```text
HTTPS
```

禁止生产环境通过 HTTP 明文提供：

```text
/login
/oauth2/*
/userinfo
/api/*
```

---

## 12.6 敏感信息保护

敏感信息包括：

- 身份证；
- 手机号；
- 邮箱；
- 密码；
- Token；
- Client Secret；
- 私钥。

日志不得输出：

```text
password
client_secret
refresh_token
private_key
身份证完整号码
```

---

## 12.7 身份证号保护

数据库：

```text
id_card_ciphertext
id_card_hash
```

其中：

```text
ciphertext
```

用于受控读取。

```text
hash
```

用于查询匹配。

推荐使用：

```text
HMAC-SHA256
```

国密场景根据密码应用方案使用相应密码算法。

---

## 12.8 管理员安全

管理员操作必须：

- Token 认证；
- 权限校验；
- 审计；
- 敏感操作二次确认；
- 高风险操作可增加 MFA。

---

## 12.9 审计安全

审计记录：

```text
INSERT ONLY
```

增加：

```text
previous_hash
log_hash
```

形成：

```text
Log1
 │
 ▼
Log2
 │
 ▼
Log3
```

通过 Hash 链发现篡改。

---

## 12.10 国密安全

国密方案由：

```text
认证中心
     │
     ▼
密码服务抽象层
     │
     ▼
密码设备/HSM
```

实现。

最终算法必须以正式密评和密码应用方案为准。

## 16.5 Token 审计

Token 生命周期审计通过以下方式实现：

1. **OpenIddict 持久化记录**：OpenIddictTokens 表自动记录 Token 状态、创建时间、过期时间、撤销状态等；
2. **sys_audit_log 事件记录**：Token 相关操作（签发、撤销、续期）通过 `event_type` 字段区分，记录到审计日志表；
3. **需求覆盖**：需求说明第二十四章要求的 Token 审计字段（ClientId、用户、签发时间、类型、撤销、过期）通过上述两种机制完整覆盖。

# 结论

V3.0 最终形成如下职责边界：

```text
                    统一认证中心
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
      身份             认证             组织
        │                │                │
        │                ├── OAuth2       ├── 单位
        │                ├── OIDC         ├── 部门
        │                ├── JWT          ├── 职务
        │                ├── SSO          └── 任职
        │                └── JWKS
        │
        ▼
     安全管理
        │
        ├── 密码
        ├── Token Version
        ├── Session
        ├── 密钥
        └── 审计


                    业务子系统
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
      角色             权限            DataScope
        │                │                │
        └────────────────┼────────────────┘
                         ▼
                    业务授权
```

最终架构原则为：

> **统一认证中心统一管理“人是谁”，业务系统自行决定“这个人能做什么”。**

> **认证中心负责身份认证，业务系统负责业务授权；认证中心负责 Token 签发，业务系统负责 JWT 本地验证；认证中心提供标准协议，不提供业务 SDK；认证中心提供统一身份上下文，但不承载业务角色、业务权限和 DataScope。**

V3.0 同时解决 V2.0 中数据库兼容、认证中心管理权限、Token 安全失效、主任职唯一性、OpenIddict 管理方式、多节点 Session、国密适配、审计完整性、接口安全及多任职等设计问题。
